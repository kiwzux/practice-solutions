## Задача 1. Поиск нетипичного поведения

Файлы сдачи: `anomalies.csv` (98 строк, 90 процессов), `analyze.py` (весь анализ), `run_log.txt` (вывод скрипта: проверки данных, маршруты, пороги).

### 1. Инструменты и шаги анализа

Python 3 + pandas/numpy. Запуск: `python3 analyze.py` в папке с `students.csv`. Скрипт печатает промежуточные таблицы и перезаписывает `anomalies.csv`; повторный запуск даёт тот же файл байт в байт.

Шаги:
1. Чтение CSV (UTF‑8 BOM, все поля как текст). Время разбирается вместе с часовым поясом; все отметки в +03:00. Внутри процесса события сортируются по числовому `EventIndex`.
2. Проверка качества исходной выгрузки (раздел 5). События после среза сохраняются для проверки качества данных, но исключаются из расчёта маршрутов, статусов и длительностей на срез.
3. Сборка заданий: `task_created` и `task_completed` соединяются по `TaskId`. Для каждого задания считаются календарная длительность и **рабочие часы** (пн–пт, 09:00–18:00). Для открытого задания считается нижняя граница ожидания до среза 01.07.2026 00:00.
4. Сборка маршрута каждой заявки: цепочка закрытых заданий с результатом (accept / return ↩ / reject ✗). Затем частоты маршрутов отдельно по типам standard / urgent / contract.
5. Профиль нормы: медиана, p95, p99 и max рабочей длительности по группам «этап × тип заявки».
6. Правила (раздел 3). Каждое срабатывание даёт отдельную строку с конкретными фактами.

### 2. Обычное поведение

Исходный журнал: 12 162 события, 1 000 заявок (635 standard, 197 contract, 168 urgent). На срез 01.07.2026 00:00 приходится 12 137 событий: 980 заявок завершены, 20 открыты. Дальнейшие расчёты поведения выполнены на этом срезе.

**Маршруты** (C — проверка, M — руководитель, D — доработка, B — бюджет, L — юрист, P — исполнение):

| Тип | Основной маршрут | Доля | Допустимые варианты |
|---|---|---|---|
| standard | C M B P → fulfilled | 77 % | один возврат C M↩ D C M B P (11 %), отказ C M✗ (4 %) |
| urgent | C M B P → fulfilled | 79 % | один возврат (14 %), отказ (4 %) |
| contract | C M B **L** P → fulfilled | 75 % | один возврат (10 %), отказ (7 %) |

- Число возвратов на заявку: 0 у 873 заявок, 1 у 119. Значений 2–4 нет вообще, затем сразу 5–8 (8 заявок). Значит, один возврат — норма, а серия возвратов — отклонение.
- Отказ всегда сразу завершает процесс. После возврата всегда идёт доработка.
- **Роли**: каждый этап закрывает своя роль (specialist, manager, requester для доработки, finance, legal, procurement). Ни у одного пользователя нет двух ролей. Единственное исключение — 8 заданий руководителя, закрытых ролью requester.
- **Длительность** (рабочие часы, медиана / p99):

| Этап | standard | urgent | contract |
|---|---|---|---|
| Проверка заявки | 0.40 / 8.0* | 0.14 / 5.8* | 0.41 / 1.3 |
| Согласование руководителем | 2.0 / 5.0 | 0.7 / 1.9 | 2.0 / 5.4 |
| Согласование бюджета | 2.6 / 7.8 | 0.9 / 2.9 | 2.5 / 7.1 |
| Проверка договора | — | — | 3.7 / 13.2 |
| Исполнение | 4.9 / 12.9 | 1.8 / 5.0 | 5.3 / 13.3 |

\* p99 завышен самими выбросами: без них максимум проверки 1.3 ч.

Срочные заявки идут примерно в 3 раза быстрее на каждом этапе. Поэтому пороги считаются отдельно для каждого типа. Переходы между этапами занимают 2–110 минут, и в них выбросов нет. Регистрация и завершение — автоматические и занимают секунды. Все действия людей попадают в рабочее время. Календарная длительность из‑за ночей и выходных бывает в 3–10 раз больше рабочей, поэтому все сравнения сделаны в рабочих часах.

### 3. Критерии поиска

Отклонения делятся на два класса:
- **Нарушение процесса** — противоречит обязательной схеме или разделению полномочий.
- **Необычно, требует проверки** — схеме не противоречит, но резко выделяется или требует бизнес‑обоснования.

| # | Правило | Класс | Почему так |
|---|---|---|---|
| 1 | Заявка исполнена без решения руководителя | нарушение | обязательный этап схемы |
| 2 | Исполнение закрыто раньше бюджета (и юриста для contract) | нарушение | порядок схемы |
| 3 | Две проверки подряд без цикла «возврат → доработка» | нарушение маршрута | повторная проверка допустима только после возврата |
| 4 | Больше 1 возврата | необычно / зацикливание | разрыв в распределении: 0–1, затем сразу 5–8 |
| 5 | Роль исполнителя не совпадает с ролью этапа; отдельно — если исполнитель является инициатором | нарушение полномочий | 1 141 из 1 149 решений руководителя приняли менеджеры |
| 6 | Внеплановая проверка (auditor) | требует обоснования | не входит в базовую схему; по условию одна редкость не доказывает нарушение |
| 7 | ≥2 заданий в заявке закрыты быстрее чем за 60 с | подозрение на формальное согласование | без этих случаев самое быстрое задание длится 3 мин (проверка), а решение руководителя — от 14 мин |
| 8 | Закрытое задание дольше max(Q3 + 3·IQR; 5 медиан) своей группы «этап × тип» | необычно (задержка) | IQR устойчив к выбросам; «5 медиан» — выбранный критерий практически значимой задержки |
| 9 | Открытое задание, у которого нижняя граница ожидания выше порога из п. 8 | зависание | открытость сама по себе не аномалия, важна длительность ожидания |
| 10 | Событие позже среза наблюдения | качество данных | противоречит описанию выгрузки |

Дополнительно проверялись правила, которые не дали срабатываний: продолжение после отказа, возврат без доработки, contract без юриста, юрист у не‑договорной заявки, действия вне рабочего времени, задержки между этапами.

Для п. 8 выбран порог max(Q3 + 3·IQR; 5 медиан), чтобы выделять статистически крайние и практически значимые задержки. Ночи и выходные уже исключены из рабочих часов, поэтому перенос на следующий день сам по себе не объясняет превышение. Порог является аналитическим критерием, а не нормативом процесса: более короткие задержки он может пропустить. По нему выделились проверки длительностью 8 и 60 ч, при максимуме остальных проверок 1.3 ч, то есть с явным разрывом.

### 5. Ложные срабатывания, ограничения, ручная проверка

**Качество данных.**
- 25 событий в 10 процессах датированы 01.07.2026 09:16–17:59, то есть после среза. Описание утверждает, что таких событий нет. По смыслу эти заявки на срез были ещё открыты. Включены в CSV с явной пометкой «качество данных», а не как поведение процесса.
- Все 1 000 заявок запустил один пользователь `5da4329a…`. Это может быть сервисная учётная запись. Тогда проверка «самосогласования» (совпадение с инициатором) ненадёжна. Те же 8 случаев всё равно остаются нарушением полномочий по роли.
- 74 % стартов приходятся ровно на 09:00:00. Видимо, заявки, поданные вне рабочего времени, регистрируются в начале рабочего дня.
- Доработку часто выполняет не инициатор, а другой пользователь с ролью requester (143 из 173). Распределение равномерное, похоже на свойство генератора. Не помечал.

**Возможные ложные срабатывания и случаи для ручной проверки.**
- *Внеплановая проверка* — по условию её оправданность нельзя установить по журналу. Связи с суммой или типом заявки нет. Нужна служебная записка или основание аудита.
- *Проверка длительностью 8 рабочих часов* — это ровно один рабочий день. Возможная законная причина — отсутствие специалиста или запрос документов. Слабее, чем 60 часов, требует уточнения.
- *Мгновенное закрытие* может быть законной пакетной обработкой или автосогласованием. Нужно проверить, какой клиент или интеграция закрывали задания.
- *Многократные возвраты* бывают при реальных повторных ошибках заявителя. Нужны комментарии руководителя.
- *Пропуск руководителя* может быть допустим, если в организации есть правило автосогласования малых сумм. Здесь суммы этих заявок от 4.9 до 99 тыс. — правило не просматривается.

**Ограничения метода.**
- Длительность задания включает ожидание в очереди, поэтому это не время работы сотрудника.
- Праздники не учитываются (по условию).
- Среди 20 открытых заявок 8 ожидают руководителя сверх порога. У остальных 12: 9 заданий на исполнении имеют возраст 0.1–4.2 рабочих часа, 2 задания юристу — 3.8 и 10.8 часа, а у одной заявки после бюджета задание на исполнение ещё не создано. Эти случаи не помечены как зависание; 10 из них отдельно отмечены за события после среза в исходной выгрузке. Для открытого задания известна только нижняя граница ожидания; длительность ещё не созданного задания неизвестна.
- Пороги для внеплановой проверки и доработки у срочных заявок построены по малым выборкам (2–26 заданий).
- Правила ловят известные виды отклонений. Совсем новый вид, который не нарушает порядок и не выделяется по времени, этим методом не найти.

### 1. Как обрабатывался журнал

Инструменты: Python 3 и pandas. Рисунки строит Graphviz `dot`. Специальные библиотеки Process Mining не использовались: DFG и алгоритм Alpha реализованы в `analyze.py` (около 40 строк), так что каждый шаг можно проверить.

Шаги:
1. Чтение CSV как текста (UTF‑8 с BOM). `EventIndex` переводится в число. Строки группируются по `ProcessInstanceId` и сортируются по **числовому** `EventIndex`.
2. Проверка данных (`run_log.txt`, раздел 1):
   - 6508 событий, 1000 экземпляров, одна версия шаблона `TemplateVersion = 1`;
   - `EventIndex` идёт 1…n без пропусков, и время по нему не убывает;
   - в каждом экземпляре ровно один `process_started` (первым) и один `process_completed` (последним);
   - `ActivityId` и `ActivityName` соответствуют один к одному;
   - сумма внутри экземпляра не меняется;
   - у каждого человеческого задания свой `TaskId`. Значит, повторы — это новые выполнения, а не дубли, и они **сохранены**.
3. Трасса экземпляра — это последовательность `ActivityName`. Из трасс получены варианты, присутствие активностей по исходам, DFG (пары a→b), а также DFG с учётом `Result` источника.
4. Каждую развилку проверяли по двум вопросам: что её определяет (`Result`, `Amount`) и есть ли исключения.
5. Автоматические модели (DFG, Alpha) сравнивались с ручной схемой. Для сравнения использовались воспроизведение трасс и перебор поведения, которое модели допускают.

### 3. Переходы и развилки

Все 12 наблюдаемых пар a→b есть в `student_transitions.csv` и на схеме. Других пар в журнале нет.

| # | Развилка (XOR) | Чем определяется | Ветки (сколько раз) |
|---|---|---|---|
| G1 | после «Первичной проверки» | `Result` проверки | accept → Согласование руководителем (1129); reject → Заявка отклонена (45) |
| G2 | после «Согласования руководителем» | `Result` согласования | accept → Проверка бюджета (911); return → Доработка заявки (174); reject → Заявка отклонена (18); cancel → Заявка отменена (26) |
| G3 | после «Проверки бюджета» | `Amount` | ≥ 150 000 → Дополнительное согласование (209); < 150 000 → Исполнение закупки (702) |

- В G1 и G2 значение `Result` **однозначно** задаёт следующую активность. Исключений нет: в `run_log`, раздел 4, проверка возвращает «True».
- В G3 результат у бюджета всегда `accept`, поэтому ветку выбирает не он. Ветку выбирает сумма:
  - без доп. согласования максимум 149 743.41 (`4794f856-…`);
  - с доп. согласованием минимум 150 614.59 (`7c26c98e-…`);
  - правило «доп. согласование ⇔ Amount ≥ 150 000» выполняется во всех 911 заявках, дошедших до бюджета.
- Другие зависимости от суммы не установлены: сравнение медиан по исходу и числу возвратов само по себе не доказывает независимость.
- **Слияния** (XOR-join), то есть активности с несколькими предшественниками:
  - `Первичная проверка` ← Регистрация (1000) / Доработка (174);
  - `Исполнение закупки` ← Проверка бюджета (702) / Доп. согласование (209);
  - `Заявка отклонена` ← Первичная проверка (45) / Руководитель (18).
- **Наблюдаемые последовательности согласуются с последовательной моделью с XOR-шлюзами.** В журнале нет ни одной пары, наблюдаемой в обоих порядках (a→b и b→a). Это не доказывает отсутствие параллельной работы: журнал содержит только завершения заданий.

### 4. Возвраты и повторные выполнения

- Единственный цикл: `Согласование руководителем (return) → Доработка заявки → Первичная проверка → Согласование руководителем`. После возврата всегда идёт именно этот фрагмент. Проверка с доработки начинается заново, а не с руководителя.
- Число доработок на заявку: 0 у 844 заявок, 1 у 138, 2 у 18 (всего 174 события в 156 заявках). Больше двух не встречается. Первичная проверка и согласование выполняются до 3 раз.
- Решения по номеру прохода (`run_log`, раздел 6):

| | 1-й проход | 2-й проход | 3-й проход |
|---|---|---|---|
| Первичная проверка | accept 955, reject 45 | accept 156 | accept 18 |
| Согласование руководителем | accept 755, return 156, reject 18, cancel 26 | accept 138, return 18 | accept 18 |

**Наблюдаемый факт:** после доработки ни разу не было отказа или отмены (0 из 174 повторных проверок и 0 из 174 повторных согласований). При независимых решениях с вероятностями отказа/отмены как на первом проходе (≈4.5 %) вероятность нуля таких исходов составила бы ≈3·10⁻⁴ для каждого вида заданий. Это ориентировочный расчёт: повторные решения внутри заявки могут зависеть друг от друга, а доработка — менять вероятность отказа. Отсутствие отказов в выборке не доказывает запрет в системе.

### 6. Факт и гипотеза

**Факты из журнала** (с учётом класса заявок):
- начало R → C у всех 1000 заявок; далее M у 955, отклонение после C у 45;
- три наблюдаемые развилки: после C и M следующая активность определяется `Result`, после B ветка согласуется с условием по `Amount`;
- выход `B → X` только при сумме ≥ 150 000;
- цикл возврата через доработку;
- три окончания;
- отсутствие пар непосредственно следующих активностей, наблюдаемых в обоих порядках; параллельное выполнение по этому журналу не исключено.

**Гипотезы**, которые журнал не доказывает:
1. **Точный порог 150 000.** Журнал говорит только, что граница лежит между 149 743.41 и 150 614.59. Значение 150 000 выбрано как правдоподобное «круглое». Неизвестно и то, входит ли граница (`≥` или `>`).
2. **Ограничение на число возвратов.** Трёх возвратов не наблюдалось. Но при частоте возврата на 2-м проходе 11.5 % у 18 заявок ожидалось бы около 2 таких случаев, а вероятность не увидеть ни одного ≈ 0.11. Поэтому «не больше двух возвратов» — **не доказанное** правило. На схеме цикл нарисован без ограничения, с подписью о наблюдаемой кратности.
3. **После доработки руководитель не отклоняет и не отменяет.** В выборке таких исходов нет; условный расчёт вероятности приведён в разделе 4. Это может быть свойство выборки или поведения людей, а не запрет в системе. На схеме из G2 ветки reject/cancel не убраны для повторного прохода: схема описывает наблюдаемые переходы, а это ограничение указано здесь как наблюдение.
4. **Комбинация «2 возврата + доп. согласование» не встретилась.** Все 18 дважды возвращённых заявок имеют сумму < 150 000. При доле крупных заявок 22.8 % вероятность этого ≈ 0.009. Однако одиночный возврат с крупной суммой встречается (V6, 21 случай), поэтому, скорее всего, это редкая комбинация, а не запрет.
5. **Что выбирает руководитель (accept / return / reject / cancel) и проверяющий,** по данным журнала не определяется. Зависимость этих решений от суммы не установлена. В журнале нет полей, объясняющих решение, поэтому эти развилки — недетерминированные XOR «по решению исполнителя».
6. **Одинаковый порядок событий не доказывает внутреннее устройство.** Например, «Проверка бюджета» всегда стоит перед «Доп. согласованием». Это может быть как последовательный шаг, так и шлюз по сумме внутри системы, создающий задание директору. Журнал видит только завершения заданий: моменты создания и автоматические шлюзы в нём не записаны.

### 7. Автоматическая модель и сравнение (усложнённая часть)

**DFG** (`dfg.png`). Граф непосредственно следующих восстановил **все** 12 переходов, начало и окончания. Ровно эти пары и попали в CSV. Но DFG допускает больше поведения, чем было в журнале. Перебор путей длиной до 15 даёт 20 трасс, разрешённых DFG, при 8 наблюдаемых, то есть 12 лишних. Например:
- `R C M D C → отклонена` и `R C M D C M → отменена` — отказ после доработки (не наблюдался);
- `R C M D C M D C M D C M B P` — три и более возвратов;
- `R C M D C M D C M B X P` — два возврата вместе с доп. согласованием;
- ребро `B → X` в DFG разрешено при **любой** сумме. Граф не умеет выражать условие по данным, поэтому правило ≥ 150 000 находится только анализом атрибута `Amount`;
- DFG не различает проходы цикла и не показывает, что решение M однозначно задаётся полем `Result`.

**Алгоритм Alpha** (своя реализация, `alpha_net.png`) восстановил плохо, и это поучительно:
- Начало, окончания и цикл через `{Регистрация, Доработка} → Первичная проверка` найдены верно. В footprint нет пар a||b. Найден и XOR-выход руководителя `{M} → {D, отклонена, отменена, B}`.
- Но развилки G1 и G3 превратились в **параллельные** ветки. Активности `M` и `Заявка отклонена` связаны прямым переходом M→отклонена, поэтому Alpha не может поместить их в одно место после `C`. Он создаёт два отдельных места `{C}→{M}` и `{C}→{отклонена}`, и `C` порождает две фишки (AND-split). То же происходит с `{B}→{X}` и `{B}→{P}`, потому что есть переход X→P.
- Итог: сеть Alpha без ошибок воспроизводит только **18 из 1000** трасс (вариант V8). Это известное ограничение Alpha: он не умеет работать с XOR-ветками, одна из которых «перепрыгивает» другую (skip / short-cut). В ручной схеме эту проблему снимают явные XOR-шлюзы.

Вывод: автоматический DFG годится, чтобы найти переходы и проверить ручную схему, и все его рёбра совпали с ручной моделью. Развилки, условия по данным и ограничения цикла получены только из ручного анализа атрибутов `Result` и `Amount` по проходам.

### 8. Ограничения и роль AI

- Журнал синтетический, в нём одна версия шаблона и 1000 завершённых экземпляров. Редкие комбинации (3 возврата, 2 возврата с крупной суммой) могли просто не попасть в выборку.
- Время между событиями включает очередь и нерабочие часы. Поэтому длительности в `run_log`, раздел 7, нельзя считать трудозатратами.
- Анализ, скрипт и отчёт подготовлены с помощью AI-ассистента (Claude). Как проверялись выводы:
  - все числа отчёта взяты из вывода `analyze.py`, а не из ответа модели;
  - каждое утверждение «всегда / никогда» проверено отдельной проверкой на полном журнале (`run_log.txt`);
  - примеры экземпляров можно найти в исходном CSV по `ProcessInstanceId`;
  - результат автоматического Alpha проверен воспроизведением трасс, что и выявило его ошибку.

### 3. Гипотеза: прямую покупку нужно поддерживать наряду с триалом

### 4. Гипотеза: есть повторные триалы на связанных аккаунтах, но нужен корректный идентификатор

**Критерий кандидата:** один непустой `device_identifier` связан минимум с двумя разными аккаунтами, имеющими отметку триала или оплаченный триальный заказ. Одна пара «идентификатор — пользователь» учитывается один раз. Найдено 728 таких идентификаторов; у 726 минимум два аккаунта имеют именно оплаченные триальные заказы.

Однако среди кандидатов 198 значений похожи на код сборки, 194 — на UUID, 336 имеют иной формат. У 182 значений, похожих на код сборки, записаны разные имена устройств. Например, `BP2A.250605.031.A3` объединяет 73 312 аккаунтов и 538 названий устройств, включая 3 463 аккаунта с триалом. Такой ключ не идентифицирует один телефон. UUID-формат сам по себе тоже не гарантирует уникальность физического устройства.

Более содержательный кандидат: хеш идентификатора `c9b55437d676543d56343f1d519762f7ebb54141aadc10b6ed96867cec5d6283`. Он связан с 14 аккаунтами, одной записью названия устройства и ОС iOS; у 12 аккаунтов есть по одному оплаченному триальному заказу. Из них 10 не имеют обычных положительных оплаченных заказов. Пример последовательности:

| user_id | Отметка триала, UTC | Нетриальных оплат |
|---|---|---:|
| 1319103 | 2026-09-02 09:44:29 | 0 |
| 1449818 | 2026-09-05 19:48:37 | 0 |
| 1551118 | 2026-09-08 21:40:20 | 0 |
| 1626714 | 2026-09-12 06:40:41 | 0 |

Интервалы близки к трёхдневному пробному периоду. Это косвенное подтверждение сценария повторных триалов, но не доказательство умысла одного человека: возможны семейное устройство, переустановка, тестовые аккаунты и коллизии ключа. Таблица устройств описывает снимок, а не момент привязки устройства к триалу.

**Предложение:** сначала исправить семантику идентификатора, затем использовать сочетание повторных триалов, временных интервалов и отсутствия обычных оплат для дополнительной проверки. По общему IP или коду сборки автоматически блокировать нельзя. В клиентских логах нет достаточной полной истории смены аккаунтов для доказательства этого сценария; основное основание здесь — сопоставление БД.

**Статус:** кандидаты на повторный триал найдены, масштаб злоупотреблений не установлен. Эффект ограничений проверять по повторным триалам и последующим оплатам с контролем ложных срабатываний.

Доказательства: [trial_device_candidates.csv](https://github.com/kiwzux/practice-task-3/blob/main/DATA.md), [trial_devices_summary.csv](https://github.com/kiwzux/practice-task-3/blob/main/DATA.md), [identifier_quality.csv](https://github.com/kiwzux/practice-task-3/blob/main/DATA.md). Хеш — SHA-256 исходного значения, необходимый для воспроизводимого поиска без публикации полного идентификатора.

### 5. Гипотеза о лимитах бесплатного тарифа: данных для выбора объёма недостаточно

Предложение из задания — подобрать оптимум вместо 500 МБ в день и 15 ГБ в месяц. Во всех предоставленных схемах нет полей счётчиков переданных байтов. В серверной истории подключений есть пользователь, нода, подписка и время; число подключений не равно объёму трафика. История рекламы содержит ID, пользователя и дату, но не размер добавленной квоты и не фактическое потребление.

В истории рекламы 7 552 651 записей у 414 504 аккаунтов; медиана — 3 записей на аккаунт за всё окно, p90 — 37. Даты: 2025-11-29 00:00:01 — 2026-09-29 11:53:44.951452. Это не дневная частота и не число подтверждённых увеличений квоты. В клиентских логах встречаются `trafficLimitReached`, `timeLimitReached` и запросы `boost-trafic`, но они не дают полного распределения потребления всех бесплатных пользователей. Сетевой access-log также нельзя суммировать как байты: записи соединений объёма передачи не задают.

**Статус:** оптимальный дневной или месячный объём не установлен; численное значение на основе этой выгрузки было бы выдумкой. Логи подтверждают наличие сценариев достижения лимитов, но выборка инцидентов смещена в сторону проблемных случаев.

Для проверки нужны суточные приращения `upload_bytes`/`download_bytes`, история тарифа на момент события, выдача и расход рекламной квоты, момент достижения лимита и стабильный идентификатор пользователя. Считать распределения нужно отдельно по активным пользователям-дням и полным месяцам. Даже такие данные ограничены действующим лимитом: наблюдаемый расход не равен желаемому. Выбор оптимума требует эксперимента с лимитами и сравнения удержания, оплат, рекламной выручки и стоимости трафика.

### 6. Гипотезы по клиентским инцидентам

#### 6.1. Повторные подключения после увеличения лимита нуждаются в понятной обработке отказа

Проверяемый пример: `logs/1000770/DAO2BF59R0.zip`, файл ` 2026-09-20T21.25.03.025.log` (пробел в начале имени сохранён).

1. Строки 315–330: запрос `POST api/v1/user/boost-trafic` в 21:27:50.891698, ответ HTTP 200 в 21:27:51.332407.
2. Строки 331–349: нажатие VPN в 21:27:54.403738, запрос конфигурации, HTTP 400.
3. Строка 373: `Error getting server config`, `status=400`.
4. Строки 441–482: новая попытка подключения примерно через четыре секунды получает тот же HTTP 400.

В соседнем файле ` 2026-09-20T20.12.03.012.log`, строка 523, ранее зарегистрирован `trafficLimitReached` в 20:51:00.206397. **Это последовательность событий, а не доказательство того, что именно лимит вызвал HTTP 400:** тело с бизнес-причиной ошибки отсутствует. Нельзя утверждать, что успешный HTTP-ответ гарантирует достаточную квоту или что пользователь действительно просмотрел рекламу перед каждым запросом.

**Предложение:** после увеличения квоты обновлять доступное состояние подключения; при отказе показывать конкретную бизнес-причину и доступное действие. Проверять долю успешных подключений после `boost-trafic`, повторные нажатия и обращения в поддержку. Наличие описанного сценария подтверждено, его причина и эффект исправления требуют проверки.

#### 6.2. Ошибки HTTP 401 следует отличать от неуспешного входа

В первом файле того же архива, ` 2026-09-20T17.48.56.048.log`, строки 49–52: несколько запросов получают 401, запускается обновление токена, остальные запросы ждут его завершения. В строке 74 — `Tokens refreshed successfully`. Такой сценарий может быть штатным восстановлением, а не потерей пользователя.

Автоматически найдена последовательность `401 → успешное обновление токена` в пределах 300 секунд внутри одного файла у 716 разных аккаунтов. Это временная связь, без строгого сопоставления каждого запроса и конкретного refresh; обновление токена не гарантирует успех всех повторённых запросов.

**Предложение:** в продуктовой метрике неуспешного входа учитывать конечный результат восстановления; отдельно измерять число повторных запросов, задержку и окончательный отказ. Сокращение лишних запросов при запуске — гипотеза, эффективность которой нужно измерять.

### 7. Дополнительная гипотеза: после неудачной оплаты стоит сохранять путь к повторной попытке

У 28 080 пользователей есть хотя бы один заказ `failed` (включая триальные заказы). У 7 668 из них (27.31 %) позднее встречается положительная нетриальная оплата. Сравниваются первая дата создания неудачного заказа и последняя дата обновления оплаченного заказа. Это наблюдаемое последующее платёжное действие, а не доля успешных повторов одного и того же заказа и не точная скорость восстановления.

**Предложение:** сохранять выбранный тариф и давать удобную повторную оплату после отказа. Проверять оплату за 24 часа и 7 дней после первой неудачной попытки, ограничивая анализ зрелыми когортами. Неудача не означает безвозвратный уход пользователя. Причина отказа и эффект нового интерфейса этими данными не доказаны. Сравнение провайдеров без учёта времени, валюты, тарифа и типа клиентов не выполнялось.

Доказательства: [order_status.csv](https://github.com/kiwzux/practice-task-3/blob/main/results/order_status.csv), [payment_funnel.csv](https://github.com/kiwzux/practice-task-3/blob/main/results/payment_funnel.csv), расчёт в `database()` файла [analyze.py](https://github.com/kiwzux/practice-task-3/blob/main/analyze.py).

### 8. Воспроизводимость и ограничения

Запуск и зависимости — [README.md](https://github.com/kiwzux/practice-task-3/blob/main/README.md). Скрипты: [analyze.py](https://github.com/kiwzux/practice-task-3/blob/main/analyze.py), [analyze_activity.py](https://github.com/kiwzux/practice-task-3/blob/main/analyze_activity.py), [check_quality.py](https://github.com/kiwzux/practice-task-3/blob/main/check_quality.py), [build_report.py](https://github.com/kiwzux/practice-task-3/blob/main/build_report.py). Денежные суммы разных валют не суммировались. Нулевая нетриальная оплата не считается покупкой.

Снимки таблиц могут отличаться по времени, история неполна; удалённые пользователи и тестовые аккаунты могут влиять на результаты. Текущая конфигурация продукта не заменяет историю тарифов. Отсутствие покупки на дату выгрузки не означает, что пользователь никогда не купит. По инцидентам нельзя оценивать частоту ошибок среди всех пользователей. Корреляции не доказывают причинность; перечисленные продуктовые изменения не являются уже подтверждённым ростом выручки или удержания.

Код и текст подготовлены с помощью AI-ассистента Codex. Числа получены программным расчётом по локальным файлам; примеры сверены со строками исходных логов. Проверки включают ключи и ссылки таблиц, раздельный учёт триала и обычных оплат, чувствительность к часовым поясам и поиск неуникальных идентификаторов. AI не использовался как источник фактов о поведении сервиса.
